Here is the comprehensive 10-rule breakdown, structured exactly as requested to help Member A implement the `GuildFlow.g4` grammar and `compiler.py` smoothly.

These are prioritized from **"Must Have" (P1)** to **"Advanced" (P3)**.

---

### **Priority 1: The Core Structure (The "Skeleton")**

*Implement these first. Without them, the compiler cannot parse any file.*

#### **1. Rule Name: Program Definition (The Root)**

* **Idea:** The absolute starting point of any file. It tells the parser, "A valid file consists of one or more definitions, followed by the end of the file."
* **Use Case:** Validating that the admin hasn't uploaded an empty file or garbage text outside a `WORKFLOW` block.
* **Example:**
* **Code:** `WORKFLOW spam_filter ON message { ... }`
* **Word-by-word:** `WORKFLOW` (Start Definition) -> `spam_filter` (ID) -> `ON...` (Content) -> `EOF` (End of File).
* **Output:** A list of definition objects (Workflows or States).


* **General Case:** `prog: definition+ EOF;`
* **System Contribution:** It acts as the container. The Visitor pattern starts here (`visitProg`) and loops through every definition found.

#### **2. Rule Name: Workflow Definition**

* **Idea:** Defines an automated bot process. It binds a unique name to a specific event trigger.
* **Use Case:** Creating a new rule called "welcome_user" that runs specifically when a new member joins the server.
* **Example:**
* **Code:** `WORKFLOW welcome ON member_join { ... }`
* **Word-by-word:** `WORKFLOW` (Keyword) -> `welcome` (Name) -> `ON` (Preposition) -> `member_join` (Event Type) -> `{` (Start Body) ... `}` (End Body).
* **Output:** `{"type": "WORKFLOW", "name": "welcome", "trigger": "member_join", "actions": [...]}`


* **General Case:** `workflow_def: 'WORKFLOW' ID 'ON' event_type ('WHERE' condition)? '{' statement* '}';`
* **System Contribution:** This creates the primary record in the `workflows` database table. The `trigger_event` is indexed so the bot finds it instantly.

### **Priority 2: Action Primitives (The "Hands")**

*These rules define WHAT the bot actually does. I have combined similar action commands into logical groups.*

#### **3. Rule Name: Messaging Actions (Send & Reply)**

* **Combination:** Combines `SEND_MESSAGE` and `REPLY_MESSAGE` as they both construct a Discord message object.
* **Idea:** Instructs the bot to send text to a specific channel or reply to the user.
* **Use Case:** Sending a welcome message to `#general` or a warning log to `#mod-logs`.
* **Example:**
* **Code:** `ACTION: SEND_MESSAGE channel=mod_logs content="User warned"`
* **Word-by-word:** `ACTION:` (Statement Type) -> `SEND_MESSAGE` (Command) -> `channel` (Param Key) -> `=` -> `mod_logs` (Param Value) -> `content` (Param Key) -> `=` -> `"User warned"` (Param Value).
* **Output:** `{"type": "ACTION", "command": "SEND_MESSAGE", "params": {"channel": "mod_logs", "content": "User warned"}}`


* **General Case:** `action_command: 'SEND_MESSAGE' 'channel' '=' ID 'content' '=' STRING | 'REPLY_MESSAGE' 'content' '=' STRING;`
* **System Contribution:** These map directly to `discord.TextChannel.send()` in your `actions.py`.

#### **4. Rule Name: Moderation Actions (Ban & Timeout)**

* **Combination:** Combines `BAN_USER`, `TIMEOUT_USER`, and `ADD_ROLE`.
* **Idea:** Enforces administrative penalties on a user.
* **Use Case:** Muting a spammer for 1 hour or banning a raider.
* **Example:**
* **Code:** `ACTION: TIMEOUT_USER duration="1h"`
* **Word-by-word:** `ACTION:` (Statement Type) -> `TIMEOUT_USER` (Command) -> `duration` (Param Key) -> `=` -> `"1h"` (Param Value).
* **Output:** `{"type": "ACTION", "command": "TIMEOUT_USER", "params": {"duration": "1h"}}`


* **General Case:** `action_command: 'BAN_USER' | 'TIMEOUT_USER' 'duration' '=' STRING | 'ADD_ROLE' 'role' '=' STRING;`
* **System Contribution:** These map to `discord.Member.timeout()` or `ban()`. The bot executes these via the Command Map.

### **Priority 3: Logic Control (The "Brain")**

*These are P3 (High Difficulty) but essential for "smart" bots.*

#### **5. Rule Name: Conditional Logic (IF/ELSE)**

* **Idea:** Branching execution. The bot evaluates a condition; if true, it does X, otherwise Y.
* **Use Case:** "If the user is an admin, do nothing. If they are a normal member, warn them."
* **Example:**
* **Code:** `IF user_role == "admin" { ... } ELSE { ... }`
* **Word-by-word:** `IF` (Keyword) -> `user_role` (Left Expr) -> `==` (Comparator) -> `"admin"` (Right Expr) -> `{` (True Block) ... `}` -> `ELSE` -> `{` (False Block) ... `}`.
* **Output:** `{"type": "IF", "condition": {"left": "user_role", "op": "==", "right": "admin"}, "then": [...], "else": [...]}`


* **General Case:** `if_statement: 'IF' condition '{' statement* '}' ('ELSE' '{' statement* '}')?;`
* **System Contribution:** The bot's runtime engine recursively executes the `then` or `else` list based on the evaluation.

#### **6. Rule Name: Trigger Filters (WHERE Clause)**

* **Idea:** A specialized condition that runs *before* the workflow even starts.
* **Use Case:** Ignoring messages that don't contain specific keywords (e.g., only run on messages containing "!help").
* **Example:**
* **Code:** `WORKFLOW x ON message WHERE content contains "!help" { ... }`
* **Word-by-word:** `WHERE` (Filter Keyword) -> `content` (Field) -> `contains` (Operator) -> `"!help"` (Value).
* **Output:** Stored in the `trigger_filter` column of the SQL table, not just the JSON blob.


* **General Case:** `condition: expr comparator expr;` (Used inside `workflow_def`)
* **System Contribution:** Optimization. The bot checks this *before* loading the full JSON logic, saving processing time.

### **Priority 4: State Management (The "Memory")**

*These rules enable multi-step flows.*

#### **7. Rule Name: State Definition**

* **Idea:** Defines a subroutine or a "step" in a process that isn't the start.
* **Use Case:** Step 2 of a verification flow: "Waiting for user to upload ID".
* **Example:**
* **Code:** `STATE awaiting_id { ACTION: SEND_MESSAGE ... }`
* **Word-by-word:** `STATE` (Keyword) -> `awaiting_id` (State Name) -> `{` (Body) ... `}`.
* **Output:** A separate JSON block, stored or referenced by the main workflow.


* **General Case:** `state_def: 'STATE' ID '{' statement* '}';`
* **System Contribution:** Allows the bot to "pause" execution and wait for the next user event.

#### **8. Rule Name: State Transition**

* **Idea:** Moving the user from one state to another.
* **Use Case:** "User has agreed to rules -> Move them to 'verified' state."
* **Example:**
* **Code:** `ENTER_STATE verified`
* **Word-by-word:** `ENTER_STATE` (Command) -> `verified` (Target ID).
* **Output:** `{"type": "TRANSITION", "target": "verified"}`


* **General Case:** `state_transition: 'ENTER_STATE' ID;`
* **System Contribution:** Triggers an SQL `UPDATE active_sessions SET current_state = ...` query.

---

### **Priority 5: Advanced Data Handling (P3)**

*The most complex rules for persistent data.*

#### **9. Rule Name: Variable Setting (SET)**

* **Idea:** Modifying persistent data associated with the user.
* **Use Case:** Incrementing a warning counter: "strikes = strikes + 1".
* **Example:**
* **Code:** `SET user.strikes = 1`
* **Word-by-word:** `SET` (Keyword) -> `user.strikes` (Variable Path) -> `=` (Assignment) -> `1` (Value).
* **Output:** `{"type": "SET", "variable": "user.strikes", "value": 1}`


* **General Case:** `set_statement: 'SET' ID '=' expr;`
* **System Contribution:** Updates the `variables` JSON column in the `active_sessions` table.

#### **10. Rule Name: Data Extraction**

* **Idea:** Pulling data from the Discord event to use later.
* **Use Case:** Getting the ID of the channel where a message was posted to use in a reply.
* **Example:**
* **Code:** `EXTRACT FIELD message.channel_id AS current_channel`
* **Word-by-word:** `EXTRACT FIELD` (Keyword) -> `message.channel_id` (Source Path) -> `AS` (Alias Keyword) -> `current_channel` (Variable Name).
* **Output:** `{"type": "EXTRACT", "source": "message.channel_id", "target": "current_channel"}`


* **General Case:** `extract_stmt: 'EXTRACT' 'FIELD' ID 'AS' ID;`
* **System Contribution:** Populates the local execution context (memory) for the duration of the workflow.
